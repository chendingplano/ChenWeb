## 9. Decision 8 addendum — kb.videos ↔ kb.images natural-key reference

Discovered while doing §6: `kb.videos.image_id` was a surrogate FK into `kb.images.id`, and `kb.images` is synced by its own independent `table_with_files` item (`kb-images`) — a raw surrogate id copied from source to target has no guaranteed relationship to the correct row in the target's `kb.images` (source/target `BIGSERIAL` sequences are independent). See design.md Decision 8.

- [x] 9.1 Use the `db-migration` skill to add `kb.images.uid UUID NOT NULL DEFAULT gen_random_uuid() UNIQUE` (`20260917000004_add_uid_to_kb_images.sql`) — a stable identifier assigned once at creation, never rewritten by `table_with_files` file materialization (unlike `stored_path`, which is).
- [x] 9.2 Use the `db-migration` skill to replace `kb.videos.image_id` with `image_uid UUID`, backfilling from the existing `image_id`→`kb.images.id` join before dropping `image_id` (`20260917000005_replace_kb_videos_image_id_with_image_uid.sql`). No `REFERENCES` constraint, matching `image_id`'s own soft-reference-only-by-comment style.
- [x] 9.3 Confirm both migrations apply cleanly via `mise dev`'s auto-migrate; check `project_db_migration` for the new version ids. Verified live: `20260917000004`/`20260917000005` applied at 2026-09-17 18:48:44; `\d kb.images` shows `uid uuid` + `kb_images_uid_key` UNIQUE; `\d kb.videos` shows `image_uid uuid` and no `image_id`; all 4 existing `kb.videos` rows' `image_uid` correctly join back to a real `kb.images.uid` (backfill verified live via a join query).
