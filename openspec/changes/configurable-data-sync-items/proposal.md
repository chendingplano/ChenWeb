## Why

Today's sync-item registry (`server/api/datasync/registry.go`) is a compiled-in Go slice — adding a syncable item means editing `registry.go` and shipping a new `server-linux` build to every box (source and target both run the same binary). It also only knows one shape of data: a plain Postgres table. A growing share of ChenWeb's admin-managed reference data is a table *plus* files on disk (`kb.videos`, and similarly-shaped tables like terminology resources) — there's no way to sync those at all today, since a bare row copy would carry the source machine's absolute file path into the target's database, pointing at a file that doesn't exist there. We need a way to (1) register a new sync item from the Sync Data admin page itself, without a code deploy, and (2) sync a table whose rows reference a file, transferring the file and rewriting the row to point at its new, local location.

## What Changes

- Add a `Kind` to sync items: `table` (today's only behavior, unchanged) and `table_with_files` (new).
- Add `kb.data_sync_items`, a table an admin can insert into at runtime via the UI. Item lookup and listing now union the compiled `Registry` with this table (compiled entries win on an id collision) — `kb_product_names` keeps working exactly as-is, unmigrated. Each row carries an `origin` of `local` (created on this instance) or `learned` (cached from a configured source via discovery, see below).
- Add **"New Data Syncher"** create/edit/delete to the Sync Data page (`POST`/`PUT`/`DELETE /api/v1/data-sync/items[/:itemId]`) where an admin picks a kind and fills in the item's shape (table, cursor column, natural key, columns, optional filter, and — for `table_with_files` — the file-reference column and where synced files land locally). A `local` item can be created, edited, and deleted; a `learned` item can only be deleted (its shape is owned by the source that defined it — editing a copy that the next discovery refresh would overwrite anyway isn't useful); a compiled item can be neither. Editing a `local` item resets its sync state (`kb.data_sync_state`), so the next sync re-fetches from scratch rather than risking a stale cursor against a changed shape. Submitted identifiers are validated as safe SQL identifiers before being persisted, since they're interpolated into generated SQL the same way compiled items' fields already are.
- Add a source-side endpoint to stream one row's file by natural key (never by a client-supplied path, to avoid exposing the source's raw filesystem layout) — extends the existing shared-secret-authenticated internal API alongside the row-changes endpoint.
- Add a source-side item-definitions endpoint (`GET /api/internal/data-sync/items`) so a target can learn about admin-created items its source now advertises — compiled items are already implicitly known everywhere since they ship in every binary, but a DB-created item only exists in the source's own database. The target write-through-caches what it learns into its own `kb.data_sync_items` on every list, so Preview/Sync keep working even if the source is briefly unreachable afterward. **BREAKING (internal API surface only, no external consumers today):** the shared-secret-authenticated internal API gains a second, still narrowly-scoped read endpoint; nothing existing changes shape.
- Extend target apply logic: for a `table_with_files` item, before upserting each fetched row, fetch its file from the source, save it under the item's configured target directory with a fresh unique local name, and rewrite the row's file column to that new path — then upsert as usual. Files, like rows, are never deleted or overwritten in place by a sync.
- Register `kb.videos` as the first `table_with_files` item, created through the new UI (not a compiled entry) as the end-to-end proof this actually works. `kb.videos` has neither a reliable change-cursor column nor a real natural key today, so this needs a small migration: add `update_time` (+ attach the existing reusable `kb.set_update_time()` trigger) and `UNIQUE(stored_path)`.

## Capabilities

### New Capabilities
- `configurable-data-sync-items`: runtime-created sync items (via admin UI, no redeploy), a second sync-item kind that transfers a referenced file alongside its row, and the cross-machine item-definition discovery needed for a target to actually use an item its source defined at runtime.

### Modified Capabilities
(none — `production-data-sync`, the capability this extends, was implemented and deployed 2026-09-15/16 but its change was never archived into `openspec/specs/`, so there is no baseline under `openspec/specs/production-data-sync/` to diff against. This change is additive to that implementation without altering any of its existing requirements — see Impact. **Decided:** rather than archiving `production-data-sync` to express this properly, `KnowledgeStore/doc-repo/devdocs/202609/2026091601-devdoc-data-sync.md` becomes the single source-of-truth document for how data sync works end-to-end, referencing both this change and `production-data-sync` for design rationale/history. Updated as the last step of this change, once implementation is verified — see tasks.md §8.)

## Impact

- **Affected code**: `server/api/datasync/registry.go` (adds `Kind`, `Origin`, file-related fields, DB-backed item CRUD/lookup, compiled+DB union); `pull_handler.go` (new per-file streaming route, new item-definitions route); `admin_handler.go` (new create/edit/delete-item routes, list route learns to merge+cache source-advertised items); `client.go` (new item-definitions + per-file fetch calls); `upsert.go`/new `files.go` (file materialization step ahead of upsert for `table_with_files` items); `server/api/routes.go` (four new routes: one internal file-fetch, one internal item-definitions, admin create/edit/delete); `project_migrations/` (new `kb.data_sync_items` table; `kb.videos` gets `update_time` + trigger + `UNIQUE(stored_path)`); `web/src/lib/components/home3/sync-data-view.svelte` + `sync-data-client.ts` (New Data Syncher button, edit/delete actions, kind-aware fields).
- **No new env vars** — reuses `DATA_SYNC_SHARED_SECRET` / `DATA_SYNC_SOURCE_URL` for the new endpoints.
- **Database**: one new table (`kb.data_sync_items`); one small `kb.videos` migration (additive columns + constraint, no data loss).
- **Deployment**: same as any other code change to `chenweb` — ship `server-linux`, migrations auto-apply on restart. No new infra (port-forward, TLS, secrets) beyond what `production-data-sync` already stood up.
- **Documentation**: `2026091601-devdoc-data-sync.md` is rewritten as the source-of-truth runbook for data sync as a whole (setup, usage, registry/CRUD, both kinds, troubleshooting), referencing `production-data-sync/` and `configurable-data-sync-items/` for the "why" behind each decision rather than duplicating it.
