## 5. Inline editor

- [x] 5.1 Wrote `inline-schema.ts` by hand (`Node`/`Mark` from `@tiptap/core`, not `@tiptap/pm` primitives directly, since `getSchema(extensions)` builds a real `Schema` from them with no live `Editor`/DOM needed — confirmed by smoke-testing schema construction directly in `bun run`). Custom `doc`/`text` nodes were required: `@tiptap/core` ships no `Document`/`Text`/`Paragraph` node at all (those live in `@tiptap/extension-*` packages bundled by `starter-kit`, which design D7 deliberately excludes), and `doc`'s content is `'inline*'` with no paragraph wrapper — one instance edits one block's inline content directly, never a block sequence
- [x] Discovered mid-schema: CDM's `code` inline type is not a wrapper like strong/emphasis/link (`content: Inline[]`) — it is a **leaf** carrying `text` directly (confirmed against `server/api/cdm/rendering/typst.go`'s `case "code": fmt.Sprintf("#raw(%q)", n.Text)` and every fixture: `{"type": "code", "text": "..."}`, never `{"type": "code", "content": [...]}`). Gave the `code` mark `excludes: '_'` so it can never coexist with strong/emphasis/link, matching that leaf shape exactly and removing an entire ambiguous case from the mapping direction below
- [x] 5.2 Wrote `inline-mapping.ts`. CDM→ProseMirror is a straightforward recursive descent (walk the nested tree, accumulate active marks entering each wrapper). ProseMirror→CDM is the harder direction and needed a real algorithm, not a per-leaf loop: ProseMirror marks are an unordered set per leaf, while CDM's wrappers are an ordered, nested tree potentially shared across many leaves. `groupByMarks` tags each leaf with its wrapper marks in a fixed canonical order (`link` > `strong` > `emphasis`, arbitrary but fixed so output is deterministic regardless of the order ProseMirror stores marks in) and recursively groups *runs* of leaves sharing a mark at each depth into one wrapper — so two adjacent bold runs become one `strong` node with two children, not two sibling `strong` nodes
- [x] 5.3 Added `inline-mapping.test.ts` (13 tests): every inline type individually, the exact `AllBlockTypes.p1` paragraph from the shared Go fixture (every type together, the strongest single proof the schema and fixture data agree), combined/nested marks (bold+italic, not exercised by either fixture but structurally legal under CDM's recursive content model), and adjacent-run merging. **Found and fixed two real bugs writing this**: (1) building CDM objects like `{type: 'citation', locator: node.attrs.locator ?? undefined}` sets an explicit `undefined` property, which `assert.deepStrictEqual` (correctly) treats as different from the key being absent — same lesson as the group 3 round-trip test, fixed with a `dropUndefined` helper; (2) a test asserting two adjacent same-mark leaves stay as two separate text children was itself wrong — ProseMirror's own `Fragment` construction already merges adjacent text nodes with identical marks before `groupByMarks` ever runs, which is the *correct* outcome, so the test's expectation was corrected instead of the code
- [x] 5.4 Added `inline-paste.test.ts` (8 tests) using `DOMParser.fromSchema` (from `@tiptap/pm/model`, a `prosemirror-model` re-export) against a DOM built by `linkedom` (added as a devDependency — confirmed empirically that ProseMirror's `DOMParser` accepts linkedom's DOM node shape with no special-casing), so this runs in plain `bun test` rather than needing a browser. private mutable copy) and wires it to `cdm-client.ts`'s
`saveDocument`/`publishDocument`/`renderDocument`/`getDocument`. `BlockList`
grew two small, narrowly-scoped additions to support it: an `editable` prop
(defaults `true`, hides every insert/delete/move/type-change control when
`false`) for the frozen/read-only state, and a `blockErrors: Map<string,
string[]>` prop that renders attributed messages under the offending block's
row and gives it a red outline.

Block/violation attribution (task 7.4) is the one piece of real logic here,
so it went into a pure module with tests rather than living inline:
`document-editor-ops.ts`'s `extractBlockId`/`attributeToBlocks`. Read through
`server/api/cdm/model/validate.go` and `server/api/cdm/store/store.go` first
to confirm the actual message shapes rather than guessing — every violation
and conflict message puts the offending block's id in the *first* quoted
substring (`block "p1" has no type`, `cdm: block id "p1" already exists in
this document`) and nothing else is quoted before it, so "first quoted
substring, or null if none" is a correct, minimal parse with no server-side
change needed. A block that fails validation for having no id of its own
(`block at position 2 in the document has an empty id`) has nothing to quote
and is correctly attributed to nothing — shown as a general (non-block)
banner instead of silently dropped or misattributed.

### `dirty` tracking (not in the task list, needed by 7.5 and 7.6)

Added a `dirty` derived value: `JSON.stringify(doc) !== savedSnapshot`, where
`savedSnapshot` is retaken after every successful load/save/publish/reload.
Considered a dedicated flag flipped by every mutation instead, but `doc.blocks`
is mutated through many independent entry points by now (`block-ops.ts`,
`table-ops.ts`, `list-ops.ts`, `InlineEditor`'s `onUpdate`, and several plain
`oninput`/`onchange` handlers directly in `BlockView.svelte`), none of which
report back to `DocumentEditor` today; a snapshot compare is correct
regardless of which path changed something, at the cost of a stringify on
access, which is unmeasurable at this MVP's document sizes.

### Found while implementing group 7

- [x] Publishing itself needed the same `dirty` guard as 7.5 describes above — this was found while writing the design, not while debugging afterward: `PublishDocument` (`server/api/cdmhandler/documents.go`) takes no body and no version, and simply publishes whatever `content_version` is currently the row's value. ### Two real bugs found while driving the full loop, both fixed

- [x] **`structuredClone` crash on navigation to a real (fetched) document.** `DocumentEditorPage`'s `doc = $state<Document | null>(null)` deep-wraps whatever it's assigned in a Svelte 5 reactive proxy; passing that proxy as `DocumentEditor`'s `initialDocument` prop then crashes at `let doc = $state(structuredClone(initialDocument))` with `Failed to execute 'structuredClone' on 'Window': #<Object> could not be cloned` — `structuredClone` cannot clone a Svelte 5 `$state` proxy. Group 7's own scratch-route verification never caught this because it seeded `DocumentEditor` from a plain JSON import, never from a value that had already passed through `$state`. Fixed by using `$state.raw` instead in `DocumentEditorPage` — correct here regardless, since this component only ever replaces the whole reference (on load or on a documentKey change), never mutates a field inside it
- [x] **A focused block's floating toolbar can hide and swallow clicks on the insert row above it.** `InlineEditor`'s toolbar (task group 5, fixed for a *different* layout-shift bug in task group 6) is `position: absolute` and floats directly above its own editor; for the topmost block, that is the same screen area as the "Insert at top" row immediately preceding it. With the first block's editor focused, its toolbar visually covers the insert row entirely and, because the toolbar's own buttons call `preventDefault()` on `mousedown` (needed so clicking Bold doesn't first blur the editor), a click aimed at "Insert at top" lands on the toolbar instead and never blurs it — reproduced deterministically with a bounding-box check confirming the overlap and a screenshot showing the insert row completely hidden behind the toolbar. Fixed with a 2-line CSS change scoped to `BlockList.svelte` (`.cdm-insert-row { position: relative; z-index: 11; }`, outranking the toolbar's `z-index: 10`), confirmed live that a second insert click now succeeds while the first block's editor is still focused. The fix makes every insert row correctly clickable; it does not address the cosmetic overlap itself (the two controls still visually overlap for a moment), which is a smaller follow-up left for later since fixing it fully would need the shared-focus registry `InlineEditor.svelte`'s own doc comment already flags as out of scope for this change
