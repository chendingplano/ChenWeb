## 6. Retire `extract_metric_definitions` from the default pipeline — ✅ ALREADY THE CASE, VERIFIED

- [x] 6.1 Confirmed the mechanism, and it's not `config.toml` (that governs `configurable`-class processors; `extract_metric_definitions` is `Class: "routed"`, `processor_plan.go`). Routed selection requires: (a) the processor's name present in the active `kb.pipelines` row's `processors[]` array, AND (b) no gate blocking it (`kb.pipeline_rules`, `OnUndetermined` as the fallback when no rule matches).
- [x] 6.2 **No change made — it's already excluded, on three independent, converging signals checked directly against the live `miner` database:**
  1. `kb.pipelines`: neither active pipeline (`all` v1, `no-entities-relations` v1) lists `extract_metric_definitions` in its `processors[]` array.
  2. `kb.pipeline_rules`: zero rows with `target_processor` matching it — no gate authorizes it.
  3. Its `ProcessorSpec` declares `OnUndetermined: "skip"` (`processor_plan.go:426`) — unlike `facet_tier1`/`facet_tier2`/`classify_document`'s `"run"` — so the no-rule-found fallback is skip, not run.

  Did not create a new `kb.pipelines` version to make this more explicit/permanent — per ADR `2026081001`, pipeline authoring is versioned and atomic (a real, higher-stakes operation), and doing that here would be a speculative change to a live config system to enforce a state that already holds, not a fix for something broken.
- [x] 6.3 Already proven true historically, not just newly tested: `kb.inputs.id=416`'s own `kb.inputs.status` history (inspected during the original code-review session) shows `extract_metric_definitions` running successfully exactly when explicitly Dev-Mode-requested (`processor_plan_facts.RequestedProcessors: ["extract_metric_definitions"]`), and never as part of an unqualified default run.
- [x] 6.4 Same evidence as 6.3, from the other direction: record 416's several default (`operation` omitted) pipeline runs over its history never produced an `extract_metric_definitions` status entry.
