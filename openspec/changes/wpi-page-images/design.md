## Context

The WPI editor (`wpi-editor.svelte`) draws the loaded page on a SvelteFlow canvas with the
interpreter's own layout and element components. `save()` builds the page JSON and calls
`savePage` (`PUT /api/v1/wpi/descriptors/page/:id`, admins only). The server stores each save
as a new version in `kb.frontend_pages`. Page attributes are checked by `validator.page` in
`server/api/wpi/validate.go`, which rejects unknown keys. `pathutil.DataHomeDir()` returns
`DATA_HOME_DIR`.

## Goals / Non-Goals

**Goals:**
- Every create/save from the editor leaves a PNG of the page in `DATA_HOME_DIR/page-images`
  and a `page_image` attribute that names it.
- The image shows the page as the author sees it, in the current display mode.

**Non-Goals:**
- Showing the image in *Load Page* or elsewhere (a follow-up; the read endpoint makes it possible).
- Server-side rendering with a headless browser.
- Deleting old images when versions are retired.
- Images for pages written directly through the admin API.

## Decisions

**D1. The browser captures the image.** The interpreter runs only in the browser, so a
capture there is exact and needs no new server component. `html-to-image` (`toPng`) renders the
page surface element of the canvas. A headless-browser service was rejected: heavy, and it would
need the page, its data and a login.

**D2. Upload first, then save the page.** `page_image` must be inside the saved descriptor, and
the page version is known only after the save. So the image gets a name that does not depend
on the version: `<descriptor_id>-<yyyymmddhhmmss>-<4 hex>.png`. The editor uploads, receives
the name, puts it in the page root as `page_image`, then calls `savePage`. Each save therefore
has its own image, and older versions keep theirs.

**D3. Endpoints.** `PUT /api/v1/wpi/page-images/:pageId` (admin; body `image/png`, at most
4 MiB, must start with the PNG signature) writes the file and returns `{ "page_image": "<name>" }`.
`GET /api/v1/wpi/page-images/:name` (any logged-in user) streams it. File names are generated by
the server from `pageId`; `:name` must match `^[A-Za-z0-9][A-Za-z0-9._-]{0,150}\.png$` and is
joined only after `filepath.Base` equals itself, so no path escapes the directory. The directory
is created on first use. With `DATA_HOME_DIR` unset the upload answers 503.

**D4. Validation.** `page_image` is an optional page attribute: a string matching the same name
pattern. The validator does not check that the file exists, so a page copied between machines
still saves.

**D5. Capture never blocks saving.** Capture or upload failure is caught; the page is saved
without a new `page_image` (a previous value is kept) and a toast warns. The editor strips
`page_image` from a *copy* only when the author uses Save As / Create Page with a new ID, since the
image belongs to the old page; the next save replaces it anyway.

**D6. Capture details.** Only the page surface is captured (not the toolbar, selection overlays
or properties panel); overlays are excluded with a `filter`. Pixel ratio 1, background taken
from the page or the theme. Capture runs after pending edits are applied, from the same
snapshot the save uses.

## Risks / Trade-offs

- `html-to-image` can miss cross-origin images or some CSS; the result is a good-enough
  thumbnail, not pixel-perfect. Mitigation: failure path in D5.
- Every save writes a PNG, so the directory grows. Accepted: images are small; cleanup is a
  non-goal.
- Auto-save/recovery writes (`savePageRecovery`) do not make images, only explicit saves do.
